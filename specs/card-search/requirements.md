## Glossary

- **Query** — the text string typed by the user to initiate a search.
- **Catalogue** — the external database of all Pokémon TCG cards (name, set, collector number, language). Used as the search index.
- **Collection** — the user's personal inventory of owned cards, stored locally. A subset of the catalogue.
- **Copy** — one physical instance of a card in the user's collection, with its own condition, location, and language.
- **Collector number** — the numeric identifier printed on the card (e.g. "025/165"), unique within a set.

## Introduction

Card Search lets a collector find any Pokémon TCG card by name — whether or not they own it. Results show the card's identity (set, collector number) alongside the user's ownership status: how many copies they own, where each is stored, and what condition it is in. If the user does not own the card, a single tap adds it to their collection.

This feature covers both lookup and quick-add. It does not cover bulk import, editing existing copies, or removing cards. The search index is an external card catalogue; the ownership data is the user's private collection.

## User stories

### US-1 · Search the card catalogue by name
**As a** collector in a shop  
**I want** to type a card name and see matching cards from the full catalogue  
**So that** I can find the card I'm looking at, whether or not I own it

**Acceptance criteria**
- 1.1 The system SHALL display matching results within 3 seconds of the user's last keystroke, measured from keystroke to results visible on screen.
- 1.2 The system SHALL begin searching after the user has paused typing; it SHALL NOT fire a new search on every individual keystroke.
- 1.3 The system SHALL match cards whose name contains the query string (case-insensitive, partial match).
- 1.4 IF the query is empty or whitespace on page load or at any time, THEN the system SHALL NOT display results and SHALL display a prompt to enter a card name.
- 1.5 IF no catalogue cards match the query, THEN the system SHALL display a clear "no cards found" message — not an empty list or blank screen.
- 1.6 The system SHALL display each result's name, set name, collector number (e.g. "025/165"), and card language.
- 1.7 IF a search returns more than 20 results, THEN the system SHALL display the first 20 and prompt the user to refine the query — it SHALL NOT display an unbounded list.
- 1.8 Card names in results SHALL be displayed in full and SHALL NOT overflow or be clipped on a 375 px wide viewport.

### US-2 · See ownership status and copy details
**As a** collector evaluating whether to buy a card  
**I want** to see immediately whether I own a matched card and the details of each copy  
**So that** I can decide to buy, skip, or upgrade

**Acceptance criteria**
- 2.1 For each catalogue result, the system SHALL display a copy count: the number of owned copies (0 or more).
- 2.2 The system SHALL display the copy count as a number — not only a colour or icon — so the distinction between 0 copies and 1+ copies is conveyed in text.
- 2.3 IF the user owns one or more copies of a card, THEN the system SHALL display each copy's condition (NM / LP / MP / HP / DMG), storage location (e.g. binder or box label), and language — inline with the search result, without navigating to a separate screen.
- 2.4 IF a card has more than 5 owned copies, THEN the system SHALL show the first 5 and offer a way to see the rest. (5 fits a single screen at minimum viewport; this threshold may be revisited once the UI is tested.)
- 2.5 IF the data read from the collection fails or returns an unexpected error, THEN the system SHALL display a distinct error message — it SHALL NOT display a copy count of 0 or a "not owned" state, which would be mistaken for correct data.

### US-3 · Search is usable on mobile in a shop
**As a** collector using a phone one-handed while browsing cards  
**I want** the search input to be immediately accessible when I open the app  
**So that** I don't waste time navigating before I can type

**Acceptance criteria**
- 3.1 The system SHALL present the search input as the primary element on the initial screen — no navigation required before typing.
- 3.2 The system SHALL enable a user to complete a full card lookup and read copy details in a single screen interaction, without navigating away from the search view.
- 3.3 The system SHALL render correctly on viewports 375 px wide and above. Desktop viewports are out of scope for this feature.
- 3.4 The system SHALL remain usable when the device is in portrait orientation.
- 3.5 WHILE a search is in progress, the system SHALL display a visible loading indicator. The indicator SHALL appear if results have not arrived within 300 ms of the triggering keystroke pause.
- 3.6 IF a search fails due to a network or server error, THEN the system SHALL display a human-readable error message and offer a retry action — not a blank screen or a raw error code.

### US-4 · Add an unowned card to the collection from search results
**As a** collector who has just found a card they want to log  
**I want** to tap a single button to add an unowned card to my collection  
**So that** I can record a new acquisition without leaving the search view

**Acceptance criteria**
- 4.1 IF a catalogue result shows 0 owned copies, THEN the system SHALL display an "Add to collection" action for that card.
- 4.2 WHILE the add action is in progress, the system SHALL display a visible indicator that the save is happening.
- 4.3 IF the add succeeds, THEN the system SHALL update the copy count for that card in the current search results without requiring a full page reload.
- 4.4 IF the add fails, THEN the system SHALL display a human-readable error message — it SHALL NOT silently discard the user's input or show a false success state.
- 4.5 The "Add to collection" action SHALL require the user to provide at minimum: condition and storage location. It SHALL NOT silently default these values without the user's confirmation.
- 4.6 The system SHALL NOT offer the "Add to collection" action for a card the user already owns via this flow (they may have zero, one, or many copies — the action appears only at zero).

## Edge cases

- **Empty or whitespace query:** covered by 1.4 — no search fires.
- **Query matches more than 20 catalogue cards:** covered by 1.7 — cap at 20 with a refine prompt.
- **Same card name across multiple sets:** covered by 1.6 — set name and collector number distinguish them.
- **User owns the same printing multiple times:** covered by 2.3 and 2.4 — all copies listed.
- **Empty collection (zero copies of everything):** the copy count of 0 is the correct "not owned" display. No special empty-state needed beyond criterion 2.2.
- **DB read returns partial or corrupt data:** covered by 2.5 — must surface as a distinct error, not a zero count.
- **Network unavailable:** covered by 3.6 — readable error + retry. Full offline mode is out of scope.
- **Add action fails mid-flight:** covered by 4.4 — error displayed, no silent discard.
- **Very long card name:** covered by 1.8 — must render in full, no overflow on 375 px.

## Non-functional requirements

- **Performance — end-to-end:** search results visible within 3 seconds of the triggering keystroke pause (P95 on a 4G mobile connection). This is the constitution's hard limit.
- **Performance — server-side:** catalogue query round-trip under 500 ms (P95). Both budgets must pass independently.
- **Device support:** iOS Safari 16+ and Chrome for Android 110+. Desktop browsers are not a target for this feature.
- **Accessibility:** search input, results list, copy detail rows, retry button, and add-to-collection action must be keyboard-navigable with visible focus states. Target: WCAG 2.1 AA. Deviations must be documented as open questions.
- **Access model:** collection data belongs to a single authenticated user. Unauthenticated access to collection data is not permitted. Authentication mechanism is deferred to a separate spec; this feature must not assume the data is public.
- **Hosting cost:** this feature must add zero recurring cost beyond the existing Vercel + Turso free tier.

## Out of scope

- Bulk import or export of collection data.
- Editing or deleting existing copies (separate feature).
- OCR / photo recognition of binder pages (explicitly deferred to v2+, not banned — the data model must not prevent it).
- Barcode scanning.
- Collection valuation or market price display (separate feature).
- Trade matching or social features.
- Decklist builder.
- Support for non-Pokémon TCGs (data model must not prevent it; this UI targets Pokémon only).
- Full offline mode (network error handling is in scope; offline-first caching is not).
- Desktop viewport optimisation.
- First-edition / print-run tracking (see OQ-4 below).

## Open questions for the human

1. **Card catalogue source (OQ-1 from intent):** ~~which external API or dataset provides the authoritative card catalogue?~~ **Resolved — see [ADR-001](../../decisions/card-search/ADR-001-use-pokemontcg-io-as-card-catalogue.md).** Decision: pokemontcg.io API.
2. **Collection entry beyond quick-add (OQ-2 from intent):** ~~bulk import needed alongside quick-add?~~ **Resolved.** Quick-add is sufficient for v1. Bulk import is deferred to a future feature.
3. **Location granularity (OQ-3 from intent):** ~~how granular is storage location?~~ **Resolved.** Binder name only (e.g. "Binder 3"). No slot-level tracking in v1.
4. **Condition scale (OQ-4 from intent):** ~~is NM / LP / MP / HP / DMG correct?~~ **Resolved.** NM / LP / MP / HP / DMG is the correct scale.
5. **First edition / print run (OQ-5 from intent):** should individual copies record first-edition status or print run? Not included in current criteria.
6. **Authentication mechanism:** the NFR requires unauthenticated users cannot access collection data. How is the single user authenticated? (e.g. magic link, password, OAuth) This belongs in a separate spec but must not be designed around.
